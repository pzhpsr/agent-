目标：把“先做什么、拿到什么、下一步用什么”说清楚，区分生成计划与执行计划。

## 1. 同一个任务，两种运行方式（约 45 分钟）

```powershell
./.venv/Scripts/python.exe -X utf8 -m xuexi_lab run --mode tools --question '读取01_统计规则.md，查询可报销类别金额，计算增加10%预留后的金额，给出CNY和依据。'
./.venv/Scripts/python.exe -X utf8 -m xuexi_lab day3
```

数据核对：差旅 550.00，办公 140.00，餐饮 170.00；规则只允许差旅和办公。
所以可报销统计为 690.00 CNY，增加 10% 预留为 759.00 CNY。
这是教学预期值，用于核对，不应写死进 Agent 的答案代码。

## 2. 观察实际计划（约 35 分钟）

在 trace 中找 `planner`、`plan.steps`、`executor`。
planner 无工具，仅输出 1–3 步 JSON 计划；executor 使用工具，并接收前面步骤的实际结果。
程序限制计划步数和总模型调用次数，不依赖“请适时停止”一句提示词。

观察：计划有没有遗漏规则？有没有在查询之前猜出金额？后一步是否使用了真实结果？
更多步骤可能增加耗时和调用，不代表准确率一定提高。

## 3. 亲手修改（约 60 分钟）

只修改 `runtime.py` 中 planner 的附加说明：要求每一步指出需要的输入及预期产出，但仍返回相同 `steps` 字符串列表。
模型、工具、问题均不变。再次运行，对比计划是否更容易检查依赖，最终结果是否正确，调用次数是否上升。

## 4. 注入一个可恢复故障（约 40 分钟）

```powershell
./.venv/Scripts/python.exe -X utf8 -m xuexi_lab day3 --question '第一步必须读取 missing.md；只有成功后才统计支出。读取失败就停止，不要换成其他文件。'
```

预期工具报告文档不存在，执行器将该步骤标为失败，后续计划步骤不再执行。
这检查的是程序级停止，不是只看模型有没有说“停止”。
离线测试 `test_failed_tool_stops_planned_workflow` 固定检查这条行为。

## 5. 验收

画出“规则 → 查询 → 计算”的依赖链，并解释如果把任一环删掉会产生什么错误。
根据 trace 比较直接执行与先规划的正确性、模型调用数和耗时，不预设哪种必然更优。
选读：Hello-Agents 第 4 章 Plan-and-Solve；LangChain Agent 与消息接口。
